# Класифікація проєкту та аналіз його оточення: ХатаHub

## 1. Класифікація проєкту

| Ознака класифікації | Обрана категорія | Обґрунтування |
|---------------------|------------------|---------------|
| Розмір проєкту | Малий | Над проєктом працює команда з 5 студентів протягом одного семестру, а бюджету в грошовому вигляді немає. Обсяг робіт — MVP із 5–7 ключовими функціями для одного гуртожитку. |
| Тип продукту | Веб-застосунок | Продукт реалізується як адаптивний веб-застосунок (PWA), який працює і на смартфоні, і на комп'ютері без встановлення з магазину застосунків. Сповіщення доповнює Telegram-бот, але основна логіка — у вебі. |
| Галузь застосування | Освіта | Продукт обслуговує студентів і адміністрацію закладу вищої освіти й покращує умови проживання, які безпосередньо впливають на навчання. Ним користуються лише учасники університетської спільноти. |
| Рівень невизначеності вимог | Середній | Базові потреби (чергування, заявки, оголошення) зрозумілі й навряд чи зміняться. Проте пріоритети функцій, вимоги адміністрації та зручність інтерфейсу уточнюватимуться після тестування з реальними мешканцями. |
| Модель співпраці | Внутрішній продукт | Продукт створюється для потреб власного університету, без зовнішнього комерційного замовника. Основними зацікавленими сторонами є студенти, адміністрація гуртожитку та викладач курсу. |
| Тип життєвого циклу | Гнучкий (Agile) | Роботу організовано короткими спринтами по 1–2 тижні з регулярною демонстрацією результатів викладачу. Такий підхід дозволяє швидко враховувати відгуки користувачів і змінювати пріоритети при середній невизначеності вимог. |

## 2. Аналіз внутрішнього оточення

- **Склад і компетенції команди.** Команда складається з 5 студентів спеціальності «Комп'ютерні науки» з розподіленими ролями: Project Manager, Product Owner, Developer, Designer, Analyst. Учасники мають базові знання HTML/CSS/JavaScript, баз даних і Git, але лише один учасник (Developer) має досвід повноцінної розробки веб-застосунків.
- **Технічні ресурси.** Кожен учасник має власний ноутбук і смартфон. Використовуються безкоштовні інструменти: GitHub (репозиторій, Issues, Projects), Figma (дизайн), Visual Studio Code, Telegram для комунікації. Для розгортання планується безкоштовний хостинг (Vercel / Render) і безкоштовний тариф бази даних (Supabase / Firebase). Платних ліцензій команда не має.
- **Часовий бюджет команди.** Кожен учасник може приділяти проєкту приблизно 4–6 годин на тиждень з урахуванням інших дисциплін, тобто загалом близько 20–30 годин на тиждень на команду. Навантаження зростає під час сесії та модульних контролів.
- **Досвід з обраною тематикою.** Частина команди проживає або проживала в гуртожитку, тому добре розуміє реальні побутові проблеми мешканців. Водночас досвіду створення систем для адміністрації (обробка заявок, звітність) у команди немає.
- **Організаційне середовище.** Проєкт виконується в межах навчальної дисципліни з фіксованими термінами здачі лабораторних робіт. Робочий процес будується на щотижневих зустрічах команди, комунікації в Telegram-чаті та веденні задач у GitHub Projects; фінальні рішення щодо обсягу погоджуються з викладачем.

## 3. Аналіз зовнішнього оточення

- **Цільова аудиторія та її потреби.** Основні користувачі — студенти 17–25 років, що проживають у гуртожитку. Їм потрібні прозорий графік чергувань, швидкий спосіб повідомити про поломку та отримати відповідь, а також єдине місце для оголошень замість розрізнених чатів. Адміністрації потрібен зручний облік звернень і канал для офіційних повідомлень.
- **Аналоги та конкуренти:**
  - **Flatastic** — мобільний застосунок для співмешканців з графіком домашніх обов'язків, спільним списком покупок і розподілом витрат. Не має зв'язку з адміністрацією та не розрахований на цілий гуртожиток; повний функціонал платний.
  - **OurHome** — безкоштовний застосунок для розподілу хатніх справ із балами та нагородами. Орієнтований на сім'ї, не підтримує заявки на ремонт, оголошення та бронювання спільних приміщень.
  - **Telegram/Viber-чати гуртожитку** — найпоширеніше «рішення» на практиці. Безкоштовні й звичні, але важлива інформація губиться серед повідомлень, немає статусів заявок і структурованого графіка чергувань.
- **Технологічні тренди.** Поширення PWA дозволяє отримати досвід, близький до мобільного застосунку, без публікації в App Store / Google Play. Популярність Telegram-ботів в Україні робить їх зручним каналом сповіщень. Доступні безкоштовні BaaS-платформи (Supabase, Firebase) скорочують час на розробку серверної частини.
- **Регуляторні та правові чинники.** Продукт обробляє персональні дані (ПІБ, номер кімнати, контакти), тому має відповідати Закону України «Про захист персональних даних» і містити згоду на їх обробку. Правила чергувань та звернень мають узгоджуватися з Положенням про студентський гуртожиток університету.
- **Партнерські системи та API:**
  - **Telegram Bot API** — для надсилання сповіщень мешканцям.
  - **Університетська пошта (Google Workspace / Microsoft 365)** — для авторизації та підтвердження статусу студента.
  - **Хостинг і BaaS (Vercel, Supabase / Firebase)** — для розміщення застосунку та зберігання даних.
  - **Web Push API** — для push-сповіщень у браузері.

## 5. Висновки

Класифікація ХатаHub як малого внутрішнього веб-проєкту із середнім рівнем невизначеності вимог прямо вказує на гнучку методологію управління. Каскадна модель (Waterfall) тут не підходить, оскільки пріоритети функцій і зручність інтерфейсу будуть уточнюватися після контакту з реальними мешканцями та адміністрацією. Тому команда обирає Scrum у спрощеному вигляді: спринти по 1–2 тижні, беклог продукту в GitHub Projects, короткі щотижневі зустрічі та демонстрація результатів наприкінці кожного спринту. Малий розмір команди дозволяє обійтися без складних процедур і формальної документації.

Найкритичнішими чинниками оточення є обмежений часовий бюджет команди та готовність цільової аудиторії перейти на новий продукт. Учасники поєднують проєкт із навчанням, тому реальний обсяг робіт обмежений, а будь-яка затримка через сесію може зсунути терміни. Із зовнішніх чинників найважливіша залученість адміністрації гуртожитку: без неї функція звернень втрачає сенс, а без активних мешканців не запрацює дошка оголошень та обмін речами. Сильним конкурентом залишаються звичні Telegram/Viber-чати, тому продукт має бути не менш зручним, ніж вони.

Уже на цьому етапі можна передбачити такі ризики: недооцінка трудомісткості розробки через брак досвіду більшості учасників; низька активність користувачів після запуску; відмова адміністрації від використання системи; перевищення лімітів безкоштовних сервісів; порушення вимог щодо захисту персональних даних. Для зменшення цих ризиків команда фокусуватиметься на мінімально життєздатному продукті (MVP), закладатиме резерв часу в кожен спринт і заздалегідь підготує текст згоди на обробку персональних даних.

Подальшими кроками команди є: проведення опитування мешканців гуртожитку для уточнення пріоритетів функцій; зустріч із комендантом для погодження процесу обробки звернень; формування беклогу продукту та користувацьких історій; розроблення прототипу інтерфейсу у Figma; вибір технологічного стеку та налаштування репозиторію для розробки. Результати цих кроків стануть основою для формалізації вимог і планування робіт у наступних лабораторних роботах.
